# PocketChat 开发路线与交付包

> **维护日期：2026-11-07。** 用户已要求优化演进路线与任务拆分，减少过细卡片造成的执行开销；本轮仅把既有规划候选对齐到当前产品 main。
> **性质**：产品内可独立阅读的目标、取舍与进入条件；不是实现结果或发布授权。
> **唯一任务入口**：[slice queue](slice-queue.md) / 其引用 issue；[首版契约](file-work.zh-CN.md) 维护
> 文件授权、提案、确认、回执和撤销。本文不再复制任务状态，后续阶段不自动变成可领取任务。

## 1. 目标与边界

保留单用户、本地优先、Python 标准库、CLI-only 定位。在已有 Session/Task 内核上，先完成
“聊天 → 授权读取 → 预览修改 → 可信确认 → 写后回执 → 持久撤销”，再按真实失败与收益扩展。
不要求普通用户手写 TaskSpec，不迁移大框架，不把多 Agent 或分布式当作成熟度等级。

ReAct 是反馈循环，显式状态记录进度，Harness 是宿主控制，Skill 是可复用方法与资源；
四者不是互斥版本。权限、停止预算、持久记录和恢复边界从首版就有，不能留到后续“安全阶段”。
规划/执行可由同一模型的不同阶段承担；只有可测收益才需要独立 Agent。

**当前源码不等于已发布能力**：下方基线来自固定 SHA 的静态读取，完整交付/发布分别查队列与
[release ledger](release-ledger.md)。既有受控 task 命令不扩大为自由 shell；文件模式的逐提案确认
不能被 task 计划或 Skill 暗中绕过。分布式/远程 worker 改变产品边界，必须另做决策。

## 2. 证据规则

### 2.1 只有五类证据可以支持设计

| 证据类型 | 允许的用途 | 记录要求 |
|---|---|---|
| 官方规范（D） | 确认公开契约和产品边界 | URL、打开日期、原文要点 |
| 本机源码/逆向结论（R） | 确认实现机制、状态机、字段和失败分支 | 文件/篇目、章节、静态深度 |
| 本机实测（V） | 确认某条路径真实发生 | 命令、解释器/版本、输出、退出码 |
| PocketChat 当前代码（C） | 确认已有能力、契约与兼容边界 | 文件、行号、测试、trace/schema |
| 热门开源库源码/文档（O） | 提供机制模式、字段语义与失败处理参考 | 仓库 URL、版本/commit、文件/章节、许可证需另行核对 |

每个结论分开记录：

- **来源类型**：官方来源 / 项目解释 / 本机实测 / 假设；
- **验证状态**：已核验 / 待核验 / 未验证；
- **适用范围**：只覆盖本次读到的版本、端点、设备或路径。

“官方文档说支持”不等于 PocketChat 已实现；“本机逆向看到符号”不等于运行已验证；“计划做”永远不能写成“已支持”。

热门开源库只能帮助回答“这类机制通常怎样建模”，不能证明某个商业 Agent 的真实实现，也不能替代 PocketChat 的兼容边界。库中的 API、类名、目录、许可证文本和示例代码不直接复制；需要复用的只是可独立重写的状态机、字段语义和失败分类。

### 2.2 查不到就逆向

如果设计需要的机制在官方文档中查不到，按以下顺序补证据：

1. 读 PocketChat 现有代码、测试、schema、trace；
2. 复用已取得的、绑定对象版本与验证边界的契约/源码分析；
3. 读热门开源库的最小相关模块，比较多种实现的共同状态和失败边界；
4. 只读取所需片段，优先源码/明文/已解包树；
5. 闭源、混淆、二进制才投入逆向成本；
6. 逆向产出必须回答来源、机制、状态、失败分支与适用范围，并标注静态深度和运行验证等级；内部题单不在公开包内提供。

证据不能只输出关键词或字符串命中；按本包实际涉及的部分回答，不要求每次重查全部项：

- 主循环是什么；
- 上下文如何装配、何时压缩；
- 工具如何注册、分派、返回；
- 权限如何判定、谁批准、超时/取消如何终态；
- 会话、checkpoint、usage、trace 如何持久化；
- 失败如何分类、重试、fallback、恢复；
- 哪些状态是事实，哪些只是 UI 或日志。

### 2.3 参考对象

参考对象按当前问题选择，不按产品排名或全量名单逐家调研。优先既有可读源码和已取得归档；
只有实现必需的未知项才继续取证。主循环、工具权限、持久化/恢复优先于外围工具全枚举。
本次设计的可执行契约均在本产品文档；未随包附原始材料的历史 R 编号只是线索，不能要求贡献者
访问另一仓库，也不能作为独立可核验的实现证据。

## 5. 五阶段路线与进入条件

| 阶段 | 用户得到什么 | 主要工作与完成条件 | 不自动引入 |
|---|---|---|---|
| **A：可信聊天与文件助手（当前）** | 同一 CLI 会话读、改、新建、验收并撤销 | 按首版契约完成真实文件黄金路径、拒绝/冲突/重启负例；确认、回执和撤销从第一版齐备 | 自由 shell、目录/glob、递归委派、插件平台 |
| **B：连续任务助手** | 一项有明确验收条件的小任务可以连续完成、中断后接续 | 复用 TaskSpec/Plan/exec/checkpoint，补易用入口、步骤证据与整体预算；修正/网络重试/恢复分开，计划变化产生新版本 | 新执行器、强制双 Agent、默认自动扩大授权 |
| **C：受控记忆与 Skill** | 同类任务复用已确认经验与方法 | 原始证据、模型工作集、长期记忆分离；先有来源/版本/作用域，再按需加载少量 Skill；固定任务集比较成功率、人工纠正、成本与延迟 | 向量库、静默长期记忆、动态插件市场、Skill 自授权限 |
| **D：有界协作** | 需要独立上下文的任务能获得专业协作 | 从已有串行委派加一个有限职责协作者；子权限不超父、共享总预算、取消传播、迟到结果不改终态；收益须优于单执行者基线 | 递归 swarm、同文件并行写、以子 Agent 自述替代验收 |
| **E：按需远程执行（条件分支）** | 必须使用另一机器环境或确有吞吐需求时可执行 | 先取得产品范围决策与真实需求数据，再设计 worker、租约/fencing、重复结果拒绝和故障隔离；先试一台远程 worker | 默认云控制面、账号池、无限扩容、放宽安全参数的自动调优 |

B–D 是优先级与验收方向，不是本轮新增批准卡。前一阶段的相关闭环证据、真实失败样例和
可比较基线齐备后才细化下一包；有明确依赖与实测理由可以调整顺序，不为“逐级升级”重构。
安全/恢复相关的必要修复不必等待某一阶段。E 可长期不做，成熟产品不以集群规模衡量。

### 5.1 任务粒度：一个交付结果，一个任务

- 首版剩余 **6 个执行单元合成 3 个交付包**；保留已有 CHANGE/CHAT/RELEASE ID，吸收旧卡而不删除追溯。
- 一个包包含契约、实现、相称测试、用户文档与一次完整范围复审；修正轮只读新增 diff，不取消既有 review cap。
- schema、纯核、CLI、测试、文档通常是包内检查点，不各开卡。一个包可多次审查后提交，也可跨会话接续。
- 50 分钟是可能存在的单次执行预算，不是产品任务切分依据；预算/租约到期先停止并留检查点，不能自动延长租约。
- 只为独立可交付价值、真实写范围/依赖冲突或不同授权边界拆包；不要把全部功能塞成不可复核的大改动。
- 当前包展开精确 scope/done_when；下一包保留交接入口；更远阶段保留目标和触发条件，不预填几十张卡。
- 进展看可复现用户任务、失败率、人工修正与有效成本，不看卡片数量。没有新改动/失败/疑虑，不重复已绿检查。

### 5.2 主循环与权责

```text
用户目标/可信授权 → 现有 Session 或 Task
  → 上下文投影与请求准入 → 模型提出回答/动作
  → 宿主参数/权限/预算校验 → 必要确认
  → 持久化意图 → 执行 → 独立回读 → 耐久回执
  → 验收、继续或停止
```

模型可见工具集与执行准入是两道检查。记忆、外部文本与 Skill 不成为授权来源；Hook 是扩展点，
不是天然安全边界，配置解析失败不能被吞成“允许”。这降低可执行危害范围，不宣称彻底解决提示注入。
会话拥有消息，任务拥有步骤，文件记录拥有副作用，策略拥有权限；trace 只关联观察，不造第二套状态。
失败时先核已发生事实，再判可重试/可补偿/待处理，不承诺任意外部副作用 exactly-once 或万能回滚。

## 6. 逆向任务模板

只有现成源码/归档不能回答实施必需的问题时才补逆向。优先作为当前交付包的有界调研检查点；
需要独立环境、真实授权或独立交付物时才单开任务，不能把每个问题都变成排队卡。记录包含：

1. **问题**：只问一个主链机制，例如“上下文压缩前后各丢了多少条消息、由谁记录”；
2. **对象和版本**：回答当前问题的实际产品/库及精确版本或提交，不要求固定对象名单；
3. **证据路径**：D 官方规范 → C PocketChat 代码 → R 顶级 Agent 逆向结论 → O 热门开源库 → 需要时再逆向二进制；
4. **机制范围**：只写本包实际涉及的循环、上下文、工具、权限或恢复问题；
5. **静态证据**：区分字符串/符号命中、接口声明和实际读到的调用/失败分支，附定位；
6. **运行验证**：列实际运行的版本、输入、结果与退出码，未运行就明确写未运行；
7. **工程结论**：我们应采用的机制、不应复制的部分、PocketChat 落点；
8. **证据缺口**：哪些字段仍不能确定；
9. **范围核对**：结论是否落在 CLI-only 范围内；若指向显式本地边界之外的工具或
   agent 执行能力，标记为「当前不做」。

## 7. 实现约束

- **先契约后代码**：先写 schema、字段定义、失败枚举和测试，再写执行路径。
- **TDD**：行为变更先观察有意义的红测试；按涉及路径覆盖成功/拒绝/失败及相关超时、取消、溢出、恢复，不为纯文档制造测试。
- **复用入口与明确所有者**：模型调用与恢复复用现有内核；不同对象各有唯一所有者，通过引用关联，不造互相竞争的状态副本。
- **最小动作面**：当前不引入新的外部动作通道；已批准的 CLI 动作保持显式与可回放。
- **事实优先与兼容**：token/cost/usage/TTFT 以 provider 实报或明确标注的观察为准，不把估计当实报。缺报在展示/独立标记中表达为 `not reported` 或 `unknown`；既有稳定 JSON 的 usage 数值字段保持缺报为 `0`，并保留未报告标记，不能直接改成字符串/null。变更需 additive 字段兼容评审或新的主版本，本次规划不授权迁移。
- **clean-room**：只借鉴机制和工程取舍，不复制第三方源码、类名、路径、业务模型或品牌素材；热门开源库也不例外。
- **版本诚实**：已发布版本边界不改写；新能力经过兼容评审后进入明确的新版本轨道。

## 8. 交付判据

每个交付包需要：可复现用户结果、实际 diff/产物、相称验证与必要复审、已知失败与未验证范围、
可接续检查点，以及现行流程要求的候选回读。只有改了 schema 才要求 schema 变更记录；纯文档
不要求产品测试、模型调用或构建。包内全部完成才结算包，临时提交不是另一个任务完成数。

运行 completed、文件 applied、验收 passed、发布完成和用户满意是不同结论。开发 wheel 的结果
不继承到最终发布 wheel；最终版本/SHA/内容变化后才做必要的重新绑定与验证。

## 9. 当前不扩的边界

自由 shell、通用远程工具、递归多 Agent、后台自主运行、Web/桌面/服务器产品、账号/云同步
仍未由本规划授权。已存在的声明式命令和串行委派不等于这些无界能力。Skill/记忆不会改变权限。
公开 push/merge/tag/Release/包上传、真实付费调用与凭据使用遵守独立批准；规划不是动作许可。
